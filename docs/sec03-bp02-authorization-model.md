# SEC03-BP02 — Authorization Model

## 1. Identification

- Workload: DepGuard Sentinel
- Pillar: Security
- Question: SEC03 — Permissions management
- Best Practice: SEC03-BP02 — Use scalable and centralized permissions management in your workload
- Assessment type: Manual evidence-based assessment
- Scope: Current internal prototype

## 2. Authorization architecture

DepGuard currently uses layered authorization controls.

### 2.1 Invoker authorization

IAM inline policy: `DepGuardHarnessInvoke`

Principal: `depguard-cli-user`

Allowed actions:
- `bedrock-agentcore:InvokeHarness`
- `bedrock-agentcore:InvokeAgentRuntime`

Resource:
- Exact DepGuardSentinel Harness ARN

The policy does not use Resource `*`.

### 2.2 Harness tool configuration

The deployed Harness configuration reports:

- Harness: `DepGuardSentinel`
- Status: READY
- Version: 2
- Allowed tools: `@analyze_manifest`

### 2.3 Local tool authorization

Source: `depguard/agentcore_client.py`

The client defines:

`_ALLOWED_TOOL_NAME = "analyze_manifest"`

The inline execution path validates the requested tool name.
Unexpected tools are rejected before local execution.
The client follows a fail-closed approach.

The `execute_inline_tool` function independently validates
the tool name and input contract.

### 2.4 Execution identity

Role: `DepGuardSentinelExecutionRole`

The role trust policy specifies:
- Principal service: `bedrock-agentcore.amazonaws.com`
- Action: `sts:AssumeRole`
- Condition: `aws:SourceAccount`
- Condition: `aws:SourceArn`

The role's permissions are managed through
`DepGuardSentinelExecutionPolicy`.

## 3. Authorization model and workload scope

The inspected implementation exposes one analysis capability:
`analyze_manifest`.

The current prototype does not demonstrate:
- Per-tenant authorization.
- Delegated user permissions.
- Dynamic resource-level access decisions.
- Different business entitlements for different customers.
- A requirement for fine-grained runtime authorization policies.

The current access model is coarse-grained:
an authorized caller can invoke the Harness, while the Harness
and local client restrict the available analysis capability.

## 4. Assessment

Provisional status: Partially Implemented.

Implemented:
- IAM-based invocation authorization.
- Resource-scoped invocation permissions.
- Harness tool allowlist.
- Local fail-closed tool authorization.
- Separate execution identity and trust policy.

Not implemented:
- A centralized application-level policy decision service.
- A shared dynamic authorization policy store.
- Centralized policy evaluation for tenant or resource entitlements.

## 5. Architectural decision

Do not introduce Amazon Verified Permissions, Cedar, or an additional
authorization service solely to satisfy this best practice.

The current prototype has one stable analysis capability and no
demonstrated requirement for dynamic, tenant-specific authorization.

Reassess this decision before introducing:
- Multiple external customers or tenants.
- Delegated permissions.
- Per-resource access rules.
- Dynamic authorization based on principal or resource attributes.

## 6. Residual risks

- Harness allowed-tool configuration and local Python allowlist
  are maintained separately and could drift.
- The current model does not provide per-tenant authorization.
- No centralized application-level authorization decision log
  has been demonstrated.
